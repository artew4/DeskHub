# 00. Архитектура DeskHub (взгляд со стороны Frontend)

> **Назначение документа:** *что* такое DeskHub, *на чём* он работает и *из каких частей* состоит — с позиции фронтенда. Первый файл слоя `Frontend_react/`.
> Общая точка входа в базу знаний — [`../README.md`](../README.md).

---

## 1. Суть проекта

**DeskHub** — персональная настольная инфо-станция (Kiosk-терминал) на базе Raspberry Pi 5 с сенсорным экраном 1024×600. Устройство постоянно включено, стоит на рабочем столе и показывает «живую» сводку: время, погоду, время в пути до работы и состояние самого устройства.

Ключевые свойства продукта:

| Свойство | Описание |
|---|---|
| **Always-on** | Работает 24/7, без участия пользователя. Должен переживать перезагрузки, обрывы сети и рестарт бэкенда без ручного вмешательства. |
| **Glanceable UI** | Информация считывается за 1–2 секунды с расстояния ~1 м. Крупная типографика, высокий контраст, минимум текста. |
| **Single-screen** | Фиксированный экран 1024×600 (карусель из двух экранов). Нет скролла, нет мелких элементов, нет «десктопного» UI. |
| **Push, not poll** | Данные приходят с сервера через SignalR. Клиент не опрашивает API по таймеру. |
| **Self-contained** | Бэкенд, фронтенд и БД разворачиваются на одном устройстве через Docker. |

## 2. Аппаратная платформа

| Компонент | Значение |
|---|---|
| Плата | Raspberry Pi 5, **8 GB RAM** |
| Архитектура | **ARM64** (`aarch64`, Docker-платформа `linux/arm64`) |
| ОС | Raspberry Pi OS (64-bit, Bookworm) |
| Экран | Сенсорный (capacitive touch), **строго 1024×600 px**, **60 Гц** (10.1" 1280×800 пробовали 08.10.2026 и вернулись — на этом дисплее масштаб 1024×600 смотрится лучше) |
| Ввод | Только тач (без клавиатуры и мыши в штатном режиме) |
| Браузер | Chromium в режиме Kiosk |
| Хранилище | microSD / NVMe SSD (рекомендуется SSD для PostgreSQL) |

### Следствия для разработки

- **Ограниченный GPU/CPU.** Анимации — только через `transform`/`opacity` (композитинг). Никаких тяжёлых `filter: blur()`, `box-shadow` на анимируемых элементах, больших полупрозрачных слоёв.
- **Device pixel ratio = 1.** Не нужно генерировать @2x ассеты; Canvas рендерится 1:1.
- **Тач-only.** Нет `:hover`-состояний как источника информации. Минимальная зона касания — 48×48 px.
- **Долгая работа без перезагрузки страницы.** Утечки памяти критичны: страница может жить неделями.

## 3. Запуск и окружение клиента

Chromium запускается автозапуском (systemd user service или `~/.config/labwc/autostart` / `wayfire.ini` в зависимости от композитора):

```bash
chromium-browser \
  --kiosk \
  --incognito \
  --app=http://localhost:5000 \
  --noerrdialogs \
  --disable-infobars \
  --disable-session-crashed-bubble \
  --disable-pinch \
  --overscroll-history-navigation=0 \
  --check-for-update-interval=31536000
```

| Флаг | Зачем |
|---|---|
| `--kiosk` | Полноэкранный режим без UI браузера |
| `--incognito` | Чистое состояние при каждом старте, нет диалогов восстановления сессии |
| `--app=...` | Открывает приложение как standalone-окно |
| `--disable-pinch` | Запрещает зум жестом щипка |
| `--overscroll-history-navigation=0` | Запрещает свайп «назад» |

> ⚠️ Из-за `--incognito` **`localStorage` не переживает перезапуск браузера**. Любые настройки, которые должны сохраняться, хранятся на бэкенде (PostgreSQL).

## 4. Архитектура доставки

### 4.1. Общая схема

```
┌──────────────────────────── Raspberry Pi 5 (linux/arm64) ────────────────────────────┐
│                                                                                       │
│  ┌──────────── Chromium (Kiosk) ────────────┐                                         │
│  │  React SPA (Vite build, static files)    │                                         │
│  │   ├─ HTTP GET  /  , /assets/*            │◄──── static ────┐                       │
│  │   ├─ REST      /api/*  (initial state)   │◄──── JSON ──────┤                       │
│  │   └─ WS        /hubs/dashboard (SignalR) │◄──── push ──────┤                       │
│  └──────────────────────────────────────────┘                 │                       │
│                                                                │                       │
│  ┌─────────────── Docker: deskhub-api (:5000) ────────────────┴─────────┐             │
│  │  ASP.NET Core (.NET 10)                                               │             │
│  │   ├─ UseStaticFiles / MapFallbackToFile("index.html")  ← wwwroot      │             │
│  │   ├─ Minimal API / Controllers   /api/*                               │             │
│  │   ├─ SignalR Hub                 /hubs/dashboard                      │             │
│  │   └─ BackgroundServices (Hosted): Weather / Traffic / Telemetry       │             │
│  └───────────────┬──────────────────────────────────┬────────────────────┘             │
│                  │ EF Core                          │ HTTP (outbound)                  │
│  ┌───────────────▼──────────────┐                   ▼                                  │
│  │ Docker: deskhub-postgres     │        Open-Meteo API, Routing/Traffic API           │
│  │ PostgreSQL                   │                                                      │
│  └──────────────────────────────┘                                                      │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.2. Принципы

1. **Один origin.** Фронтенд раздаётся тем же ASP.NET Core-процессом (`UseStaticFiles` + `MapFallbackToFile("index.html")`). Нет CORS, нет отдельного nginx.
2. **Multi-stage Docker build:**
   - Stage 1 (`node:lts`) — `npm ci && npm run build` → `dist/`.
   - Stage 2 (`mcr.microsoft.com/dotnet/sdk`) — `dotnet publish`.
   - Stage 3 (`mcr.microsoft.com/dotnet/aspnet`) — runtime + копия `dist/` в `wwwroot/`.
3. **Целевая платформа `linux/arm64`.** Сборка через `docker buildx build --platform linux/arm64` (на CI или на самом Pi). Все базовые образы обязаны иметь arm64-вариант.
4. **docker-compose** поднимает `api` (`deskhub-api`) и `postgres` (`deskhub-postgres`), с `restart: unless-stopped` и healthcheck'ами.
5. **Телеметрия хоста.** Контейнер API получает доступ к метрикам хоста через read-only монтирование (`/proc`, `/sys/class/thermal`) или через отдельный лёгкий агент — детали в документации бэкенда.

### 4.3. Поток данных

1. Браузер загружает `index.html` и бандл.
2. SPA делает REST-запрос за **начальным снимком** состояния (`GET /api/dashboard/snapshot`) — экран заполняется сразу, без ожидания push-событий.
3. SPA подключается к SignalR-хабу `/hubs/dashboard`.
4. Фоновые сервисы бэкенда периодически опрашивают внешние источники и хост, сохраняют результат (при необходимости — в PostgreSQL) и **пушат** обновления всем клиентам.
5. При реконнекте клиент повторно запрашивает снимок, чтобы закрыть «дыру» в данных.

## 5. Основные модули

| Модуль | Описание | Источник данных | Частота обновления (ориентир) |
|---|---|---|---|
| **Live Dashboard** | Карусель экранов (свайп): главный — часы, погода, пробки/кот, календарь; системный — телеметрия. Автовозврат на главный через 30 с | Локальное время + агрегат виджетов | Часы — каждую секунду (локально) |
| **Погода (Weather)** | Текущая температура, осадки, УФ-индекс, почасовой прогноз | Open-Meteo → бэкенд → SignalR | Раз в 10–15 мин |
| **Пробки (Traffic/Route)** | Время в пути по маршрутам («Дом → Работа»), уровень загруженности | Routing/Traffic API → бэкенд → SignalR | Раз в 2–5 мин (в часы пик чаще) |
| **Телеметрия (Telemetry)** | CPU, RAM, температура SoC, аптайм Raspberry Pi — на системном экране (индекс 1) | Хост (`/proc`, `/sys`) → бэкенд → SignalR | Раз в 1–2 с |
| **Тамагочи (кот)** | Виртуальный питомец в комнате на месте пробок вне окна поездки (Пн–Пт 10:00–13:20); случайные занятия, реакция на тап | Локально (состояния, таймеры) | Смена занятия раз в 10–40 с |
| **Календарь (Calendar)** | Органайзер на главном экране: сетка месяца с цветными точками календарей + повестка на сегодня/завтра | Несколько .ics (iCloud, Outlook) → бэкенд (`CalendarWorker`, Ical.Net, слияние, цвет источника) → SignalR | Раз в 15 мин; сетка/«сейчас» — раз в минуту локально |

Детальное описание фронтенд-части модулей:
- [`Core.md`](Core.md) — каркас приложения.
- [`Feature_Dashboard.md`](Feature_Dashboard.md) — главный экран и часы.
- [`Feature_Widgets.md`](Feature_Widgets.md) — виджеты Погода / Пробки / Телеметрия.

## 7. Глоссарий

| Термин | Определение |
|---|---|
| **DeskHub** | Название проекта и устройства — настольная инфо-станция. |
| **Kiosk mode** | Режим Chromium, в котором браузер занимает весь экран без адресной строки, вкладок и системных диалогов. |
| **Live Dashboard** | Главный экран приложения (индекс 0 карусели): часы, погода, пробки, календарь. |
| **Screen Carousel** | Горизонтальная карусель экранов со свайпом (`ScreenCarousel`); неглавный экран возвращается на главный через 30 с без касаний. |
| **Widget (Виджет)** | Самостоятельный блок UI с одной темой данных (Погода, Пробки, Телеметрия). Имеет собственный слайс состояния и SignalR-подписку. |
| **Card (Карточка)** | Визуальный контейнер виджета в сетке (фон, скругление, отступы, заголовок). |
| **Snapshot (Снимок)** | Полное текущее состояние всех виджетов, отдаваемое REST-эндпоинтом при старте и после реконнекта. |
| **Hub** | SignalR-хаб на бэкенде (`/hubs/dashboard`), через который сервер пушит события клиентам. |
| **Push-событие** | Сообщение, инициированное сервером через SignalR (например, `WeatherUpdated`). |
| **Polling** | Периодический опрос сервера клиентом по таймеру. **Запрещён** для получения данных на фронтенде. |
| **Stale data (Устаревшие данные)** | Данные, время жизни которых превысило допустимый порог (например, погода старше 30 мин). Должны визуально помечаться. |
| **Telemetry (Телеметрия)** | Метрики самого Raspberry Pi: загрузка CPU, использование RAM, температура SoC, аптайм. |
| **SoC** | System on Chip — процессор Raspberry Pi (BCM2712). Его температура — ключевая метрика троттлинга. |
| **Throttling** | Снижение частоты CPU при перегреве (у Pi 5 начинается около 80–85 °C). |
| **Open-Meteo** | Бесплатный публичный API прогноза погоды без ключа; опрашивается только бэкендом. |
| **Congestion level (Уровень загруженности)** | Нормализованная оценка пробок: `free` / `normal` / `heavy` / `severe`. |
| **Burn-in** | Остаточное изображение на экране от долго неподвижных элементов; минимизируется сдвигом пикселей и ночным затемнением. |
| **Night mode** | Режим пониженной яркости/контраста в ночные часы. |
| **arm64 / aarch64** | 64-битная архитектура ARM, целевая платформа Docker-образов. |
