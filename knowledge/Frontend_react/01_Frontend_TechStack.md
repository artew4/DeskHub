# 01. Frontend: технологический стек и обязательные правила

> **Назначение документа:** перечень технологий и **жёстких правил**, которые обязательны для любого кода в проекте. Правила с пометкой **MUST** не обсуждаются без обновления этого файла.

---

## 1. Стек

### 1.1. Frontend

| Слой | Технология | Примечание |
|---|---|---|
| Фреймворк | **React 18+** | Только функциональные компоненты и хуки |
| Сборка | **Vite** | `vite build` → статические файлы в `wwwroot` бэкенда |
| Язык | **TypeScript** (`strict: true`) | `any` запрещён (кроме изолированных адаптеров с комментарием) |
| Стили | **Tailwind CSS** | Дизайн-токены в `tailwind.config.ts` |
| Графика | **Canvas 2D** / **SVG** | Для графиков телеметрии и спарклайнов |
| Real-time | **@microsoft/signalr** | Единственный канал live-данных |
| State | **Zustand** | См. [`Core.md`](Core.md) |
| Линт/формат | ESLint + Prettier | Проверяются в CI |
| Тесты | Vitest + React Testing Library | Логика стора, форматтеры, маппинг DTO |

### 1.2. Backend (контекст)

| Слой | Технология |
|---|---|
| Runtime | .NET 8/9, ASP.NET Core |
| Real-time | SignalR (хаб `/hubs/dashboard`) |
| БД | PostgreSQL + EF Core |
| Статика | `UseStaticFiles()` + `MapFallbackToFile("index.html")` |
| Фоновые задачи | `BackgroundService` / `IHostedService` |

### 1.3. Инфраструктура

- Docker (multi-stage), платформа **`linux/arm64`**, docker-compose.
- Chromium Kiosk на Raspberry Pi 5.

## 2. Правила UI и вёрстки

### 2.1. MUST: Фиксированное разрешение 1024×600

- Приложение проектируется **только** под вьюпорт **1024×600 px**. Адаптивность под другие экраны **не требуется** и не должна усложнять код.
- Корневой контейнер имеет фиксированный размер:

  ```css
  html, body, #root {
    width: 1024px;
    height: 600px;
    margin: 0;
    overflow: hidden;
  }
  ```

  В Tailwind: `w-[1024px] h-[600px] overflow-hidden`. Значения выносятся в токены (`screen-w`, `screen-h`).
- Для разработки на десктопе допускается dev-обёртка, центрирующая «экран» 1024×600 с рамкой. В production-сборке её нет.

### 2.2. MUST: Никакого скролла

- `overflow: hidden` на `html`, `body`, `#root` и всех контейнерах-лэйаутах.
- Контент обязан помещаться в отведённую область. Если данные не помещаются — **обрезаем/сокращаем** (truncate, ограничение количества элементов), а не скроллим.
- Запрещены: `overflow-auto`, `overflow-scroll`, `overflow-y-*` (кроме `hidden`) — проверяется линтером/ревью.
- Отключить «резиновый» overscroll: `overscroll-behavior: none`.
- Отключить системные тач-жесты: `touch-action: manipulation` (глобально), `touch-action: none` для Canvas.

### 2.3. MUST: Tailwind как единственный способ стилизации

- Стили пишутся утилитами Tailwind в JSX. CSS-модули и styled-components не используются.
- Глобальный CSS (`index.css`) — только `@tailwind` директивы, reset под киоск и `@font-face`.
- Цвета, размеры шрифтов, радиусы и отступы — только из токенов конфига. Произвольные значения (`text-[37px]`) допустимы лишь для уникальных случаев (например, гигантские часы) и фиксируются в токенах при повторном использовании.
- Тёмная тема — основная (и единственная по умолчанию). Ночной режим — через переключение класса на корне.
- Условные классы — через `clsx` / `tailwind-merge` (`cn()` хелпер).

### 2.4. MUST: Тач-first

- Минимальная зона касания — **48×48 px**.
- Никакой информации, доступной только по `:hover`.
- Обратная связь на тап — `active:` состояния (`active:scale-95`, `active:opacity-80`), длительность ≤ 100 мс.
- Выделение текста и контекстное меню отключены: `select-none`, `-webkit-touch-callout: none`, `onContextMenu={e => e.preventDefault()}` на корне.
- Прятать курсор: `cursor: none` в production.

### 2.5. Типографика и читаемость

- Шрифт с табличными цифрами (`font-variant-numeric: tabular-nums` → Tailwind `tabular-nums`) для всех изменяющихся чисел — иначе цифры «прыгают».
- Минимальный размер текста — 14 px; основные значения — от 24 px; часы — 120+ px.
- Высокий контраст (WCAG AA минимум) — экран читается с расстояния.

## 3. Правила производительности и анимации

### 3.1. MUST: Стабильные 60 FPS

Бюджет кадра — **16.6 мс** на слабом GPU Raspberry Pi.

- Анимировать **только** `transform` и `opacity`. Запрещено анимировать `width`, `height`, `top`, `left`, `margin`, `box-shadow`, `filter`.
- `will-change` — только точечно и временно (на время анимации), не глобально.
- Избегать `backdrop-filter: blur()` и больших полупрозрачных наложений.
- Предпочтительны CSS-transitions / keyframes. Для сложной оркестрации — **Framer Motion** (`motion`) с `transform`-анимациями; добавление библиотеки фиксируется здесь.
- Анимации учитывают `prefers-reduced-motion` (на случай отключения через флаг).

### 3.2. Рендеринг React

- Частые обновления (телеметрия раз в секунду, часы) **не должны** вызывать ре-рендер всего дашборда:
  - подписка на стор через селекторы (`useStore(s => s.telemetry.cpu)`);
  - тяжёлые виджеты — в `React.memo`;
  - Canvas-графики рисуются императивно через `ref`, без ре-рендера React на каждую точку.
- Никаких `setInterval` в компонентах без очистки в `useEffect` cleanup.
- Профилирование — React DevTools Profiler + Chrome Performance на реальном Pi перед релизом фичи.

### 3.3. Долгая работа (24/7)

- Буферы истории (графики) — **кольцевые буферы фиксированного размера**.
- Все подписки (SignalR `.on`, таймеры, `requestAnimationFrame`, `ResizeObserver`) отписываются при размонтировании.
- Контроль утечек: heap snapshot после 24 ч работы не должен расти неограниченно.
- Ошибки рендера ловятся `ErrorBoundary` на уровне каждого виджета — падение одного виджета не роняет экран.

### 3.4. Размер бандла

- Цель: **< 300 KB gzip** для начальной загрузки.
- Никаких тяжёлых чарт-библиотек (Chart.js, Recharts, ECharts) без обоснования — графики на Canvas/SVG вручную.
- Иконки — tree-shakable (`lucide-react`) или inline SVG.
- Шрифты — локальные (`@fontsource/*` или файлы в `public/`), **без** CDN: устройство может работать без интернета.

## 4. Правила работы с данными

### 4.1. MUST: SignalR для real-time, без клиентского поллинга

- Все live-данные приходят **push-событиями** через SignalR-хаб `/hubs/dashboard`.
- **Запрещено** использовать `setInterval`/`setTimeout` + `fetch` для периодического опроса API.
- REST (`fetch`) используется **только** для:
  1. начального снимка состояния при старте (`GET /api/dashboard/snapshot`);
  2. повторного снимка после реконнекта SignalR;
  3. команд пользователя (изменение настроек и т.п.).
- Клиент **никогда не ходит во внешние API** (Open-Meteo, сервисы маршрутов) напрямую — только через свой бэкенд.

### 4.2. Контракты

- Все DTO описываются TypeScript-типами в `src/shared/api/types.ts` и зеркалят C#-модели.
- Имена событий хаба — константы (`HubEvents.WeatherUpdated`), а не строковые литералы по коду.
- Даты передаются в ISO 8601 (UTC), форматируются на клиенте с учётом локали `ru-RU` и таймзоны устройства.
- Каждое сообщение содержит `updatedAt` — клиент по нему определяет «устаревшие» данные.

### 4.3. Отказоустойчивость

- Потеря соединения не должна ломать UI: показываются последние известные данные + индикатор «нет связи».
- Автоматический реконнект с бесконечными повторами (см. `Core.md`).
- Если бэкенд недоступен при старте — экран-заглушка с часами (часы работают локально) и повторными попытками подключения.

## 5. Правила кода

- **Feature-based структура** (`src/features/<feature>/`), общие вещи — в `src/shared/`.
- Один компонент — один файл, `PascalCase.tsx`. Хуки — `useCamelCase.ts`.
- Именованные экспорты, без `export default` (кроме случаев, требуемых инструментами).
- Бизнес-логика (форматирование, расчёт статусов, маппинг DTO) — в чистых функциях, покрытых тестами, а не внутри JSX.
- Никаких `console.log` в production-коде; логирование — через тонкую обёртку `logger`.
- Импорты через алиас `@/` → `src/`.
